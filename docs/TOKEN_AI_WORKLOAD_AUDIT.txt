1) EXECUTIVE SUMMARY
================================================================================

* There are NINE (9) independent, pool-backed AI workloads, declared in one
  place: `config.GEMINI_POOLS` (app/config.py:2753). They are:
  intent, chat, moderation, transcribe, tts, awareness, memory, live_voice,
  search.

* Every one of them runs on Google Gemini (`google-genai`) EXCEPT the search
  workload, which is currently switched to a different vendor (Tavily) by
  `SEARCH_PROVIDER=tavily` in `.env`. Search therefore consumes a Tavily
  credential at runtime, not a Gemini key.

* There are 15 unique Gemini credential VALUES in `.env`, mapped onto 26 pool
  assignment slots (see section 3 for the slot-vs-unique distinction). One more
  unique Gemini credential exists at runtime in the owner-managed key store
  (`/data/gemini_keys.json`), for awareness. That gives 16 unique Gemini
  credentials reachable at runtime. Plus 1 Tavily credential = 17 unique
  AI-vendor credentials in total.

* Two credential VALUES are shared across workloads:
    - fp 24b50725  is used by BOTH `awareness` (slot 2) AND `chat` (slot 5).
      This is the duplicate the owner flagged; it is the SAME Google project in
      two workloads, which is exactly the collision the awareness isolation
      rationale exists to prevent.
    - fp 20ed3899  is used by BOTH `live_voice` (slot 1) AND `search` (slot 1).
      Whether this is intentional is UNKNOWN / NEEDS VERIFICATION.

* The `tts` workload has no key of its own by design: it reuses the chat
  prefix, so its 9 slots mirror chat's 9 slots exactly. This is a deliberate
  architectural share (speech synthesis is a fallback, not an authority).

* Isolation that matters structurally is keyed by WORKLOAD in the database:
  `gemini_accounts (workload, slot)`, `gemini_models (workload, slot, model)`,
  and daily counters via `db.daily_for(workload, day)`. So even a shared key
  does not share histories, rate windows, breakers or daily allowances between
  workloads. What a shared key DOES share is the provider-side (Google project)
  rate limit, which no per-workload counter can partition.

* `memory` and `state` have NO dedicated AI credential and NO model call in the
  current configuration: they are deterministic-only. `memory` would need a new,
  separate-project key to ever make a provider call, and its config var is not
  even documented in `.env.example` (section 8).

* The shared pool (`GEMINI_KEY_1.._20` + `GEMINI_POOL_KEYS`) is EMPTY on this
  deployment (SHARED_POOL_KEYS count = 0). Only `intent` opts into it, so the
  opt-in is currently inert.

* Result: the deployment is broadly well-isolated per workload, with exactly two
  cross-workload credential collisions to resolve, and one documentation gap.

7) SECURITY / ISOLATION AUDIT
================================================================================

The isolation model has two layers, and it is important to keep them apart:

  LAYER A — structural isolation (ALWAYS holds, keyed by workload in SQLite):
    * histories, rate windows, circuit breakers, failure state and daily
      allowances are keyed by WORKLOAD. So awareness never spends chat's
      allowance, memory never spends awareness's, etc., EVEN IF two workloads
      share a credential.
    * tables: `gemini_accounts (workload, slot, ...)`,
      `gemini_models (workload, slot, model, PRIMARY KEY(workload,slot,model))`,
      `gemini_discovery (fingerprint)`, and daily counters via
      `db.daily_for(workload, day)`.

  LAYER B — provider isolation (holds ONLY when the credential VALUE differs):
    * a shared credential means a shared Google project, and therefore one
      provider-side rate limit that no per-workload counter can partition.

Per workload:

  Chat
    - 9 slots, 8 unique values. One of them (slot 5) is NOT unique (see below).
    - Structural isolation: full. Provider isolation: 8 of 9 keys isolated; the
      one shared key is shared with awareness.

  Awareness
    - 2 `.env` values + 1 runtime store value.
    - Deliberate design: NO shared-pool fallback; with no awareness key the
      workload does no work at all (fail-closed). This is correct and intended.
    - DEFECT: awareness slot 2 (fp 24b50725) is the SAME value as chat slot 5.
      This directly contradicts the stated rationale for awareness having its
      own key ("sharing a credential means sharing one provider-side rate limit
      ... the collision cost 26% of conversational turns to rate limits").
      Effective result: awareness has only ONE fully-isolated key. This is the
      highest-priority finding of this audit.

  Intent
    - 2 unique values. The only workload that MAY draw on the shared pool, which
      is empty here, so no cross-workload credential is actually shared.

  Memory
    - No credential, no model call, no shared anything. Fully isolated by being
      absent.

  Transcription
    - 1 unique value, dedicated, not shared. Capability-gated to audio_in.

  Moderation
    - 1 unique value, dedicated, not shared.

  Live voice
    - 1 value shared with the dormant search Gemini key (fp 20ed3899). Since
      SEARCH_PROVIDER=tavily, search does not currently consume that value, so
      there is no live collision TODAY — but switching SEARCH_PROVIDER back to
      gemini would immediately put live_voice and search on one project.

  TTS
    - Deliberately shares chat's credential. Architecturally justified: TTS is
      optional and its failure falls back to text; it must not consume the
      answer's allowance. It has its own pool entry/breaker, so it does not
      spend chat's breaker even though it shares the key. The residual cost is a
      shared provider-side limit between chat and TTS — an accepted trade.

DELIBERATE SHARED CREDENTIALS (by design, with reason):
  * tts -> chat's keys. Reason: speech is a fallback; must not spend the
    answer's allowance; own breaker.
  * intent -> shared pool (opt-in). Reason: the classifier is the cheapest,
    most tolerant workload; inert here because the pool is empty.

ACCIDENTAL / UNVERIFIED SHARED CREDENTIALS:
  * chat:5 == awareness:2 (fp 24b50725). Likely the owner's "duplicate" token
    that was meant to be unused. It is IN USE by two workloads. Fix: give
    awareness a genuinely different key (see section 9).
  * live_voice:1 == search:1 (fp 20ed3899). Intent unknown.

PRIVACY / LOGGING
  * No message content is written to logs by the pool or the workloads; this
    audit found no place where a credential value would be logged. `app/
    agent_bridge.py` additionally scrubs secret-like strings (including an
    "openai-ish" sk- pattern) as a defence in depth.
  * `.env` and `data/` are gitignored; the key store lives inside the data
    volume and is a separate file from the database, so a support copy of the
    DB is not also a keyring.

9) NEW TOKEN ALLOCATION PLAN
================================================================================

This plan is derived from the REAL architecture and consumption above, not from
a guessed percentage. "A token" means one credential value from a Google project
that is DIFFERENT from every other key in use.

Priority order:

  1st new token -> AWARENESS.
     Why: awareness is the highest-volume workload and is the one whose entire
     isolation rationale is a dedicated project. Today it has only ONE
     fully-isolated key, because slot 2 duplicates chat slot 5 (fp 24b50725).
     Giving awareness a genuinely different key restores the intended
     two-account isolation and removes the accidental chat<->awareness provider
     collision. This is the single highest-value token.
     Expected effect: awareness stops sharing a provider rate limit with chat;
     the "26% of turns lost to rate limits" class of failure cannot recur from
     this cause.

  2nd new token -> LIVE_VOICE.
     Why: live_voice currently shares its only key with the (dormant) search
     Gemini key. If SEARCH_PROVIDER is ever switched back to gemini, or if both
     are used, they collide on one project. A dedicated live key keeps the call
     workload isolated as the architecture intends.
     Caveat: Voice Live ALSO needs TELEGRAM_API_ID/API_HASH before it can run at
     all — a new Gemini key alone does not unblock it.

  3rd new token (OPTIONAL) -> CHAT.
     Why: chat already has 8 unique keys and a per-account daily budget of 500.
     It is comparatively well-supplied. A 9th token adds headroom but is not
     required to fix any collision. Add it only if chat's rate-limit/allowance
     pressure is observed.

  SHARED POOL (GEMINI_KEY_1.._20 / GEMINI_POOL_KEYS): seed ONLY IF intent needs
     more capacity. Intent is the only workload that opts in, and the pool is
     empty today. Adding a key here helps intent (and only intent) without
     touching any other workload's isolation. Do not put a chat/awareness key
     here — that would re-couple them.

WORKLOADS THAT NEED NO NEW TOKEN:
  * Moderation     — 1 dedicated key, low volume (daily 500).
  * Transcription  — 1 dedicated key, low volume (daily 300).
  * Search         — runs on Tavily; a Gemini token is irrelevant while
                     SEARCH_PROVIDER=tavily. If search becomes the bottleneck,
                     the lever is a second TAVILY key (different vendor), not a
                     Gemini key.
  * Memory         — deterministic-only; a token would only be needed if the
                     owner decides to enable model extraction, and then it must
                     be a NEW separate-project key (never chat's or awareness's).
  * State          — no model call; no token ever.
  * TTS            — deliberately shares chat's keys; do NOT give it a token
                     (that would break the "fallback must not spend the
                     answer's allowance" design).

DUPLICATE HANDLING:
  The owner stated one of the recently-supplied tokens is a duplicate and must
  not be used. This audit identifies that duplicate concretely: it is the value
  with fp 24b50725, which is simultaneously GEMINI_AWARENESS_API_KEY_2 and
  GEMINI_CHAT_API_KEY_5. Because `_pool_key_list` de-duplicates WITHIN a single
  workload's list but NOT ACROSS workloads, the value is legitimately present in
  two pools. It should be replaced on the awareness side with a fresh key (see
  priority 1 above) so awareness regains a unique credential.
