      `act.why[0]`. O scored only the QUOTED DIRECTIVE
      (act_copula_directives). The reason string itself is unscored.
    - Evidence needed: a corpus case that renders the block beside a block that
      can contradict it. That is what made K and Q findable.

(b) CONVERSATIONAL STATE (item 5) — the half that does not exist
    What exists: `room_state` (reply graph + thread, per window), and the
    `awareness_state` row (topic, summary, participants, intent, about_user_id,
    passes, relevant). What does NOT exist: any state that carries a
    conversation ACROSS passes beyond that row — no record of what the server
    itself read, no unresolved-question lifecycle, no "the room was asked X and
    has not answered" across windows. `open_questions` is window-scoped by
    construction (it tests the reply edge in the batch).

(c) INTENT <-> AWARENESS INTEGRATION (item 12) — a concrete, verified gap
    `awareness.record` stores ONLY the model's decision fields (relevant, topic,
    summary, intent, about). NONE of the deterministic readers' output is
    recorded. So after a pass the server cannot answer "what did *I* read in
    that message?" — the act, the polarity, the object, the time direction, the
    entity, the referent verdict are rendered into the prompt and then thrown
    away. The recorded `about_user_id` is rendered back as "About then: ..." in
    `memory_block`, which is the one place the two halves touch.
    This is the largest remaining piece and it is the one the owner's item 12
    names. It touches the RUNTIME PATH.

(d) INTELLIGENT / ADAPTIVE AWARENESS SCHEDULING (items 10 and 11)
    What exists: a derived gap (remaining allowance vs seconds left in the API
    day, floored at the minimum interval), a PER-ROOM brake, a debounce
    (NEXUS_AWARENESS_DEBOUNCE_SECONDS = 8), a max wait
    (NEXUS_AWARENESS_MAX_WAIT_SECONDS = 45), a tick
    (NEXUS_AWARENESS_TICK_SECONDS = 15), NEXUS_AWARENESS_MIN_INTERVAL_SECONDS =
    20, NEXUS_AWARENESS_MAX_CHATS_PER_TICK = 2, and a daily allowance of 200
    requests (the owner keeps it at 200 and declined to trade spend for cadence;
    REQUESTS, not tokens, are the rationed currency).
    What does NOT exist: any use of the READERS' evidence to decide which room
    gets the next pass. And there is a hard design constraint: the invariant
    "`awareness.due` cannot see messages — its signature is asserted" means
    content-aware scheduling cannot be bolted onto `due`. It would need a
    different seam (e.g. the pass records a cheap hint that a later scheduling
    decision reads, without `due` ever seeing a message). That seam does not
    exist and is an OPEN DESIGN QUESTION, not a scoped change.
    Touches the RUNTIME PATH.

(e) MODEL / GEMINI ROUTING (item 13)
    Not started, and deliberately so: the standing rule is "only if benchmarks
    prove it". No benchmark in this repo measures model quality (the benchmark
    is deterministic by construction and never pretends to measure the model's
    judgement). There is also an invariant against dropping to a smaller model.
    Evidence required before this can even be scoped: a measurement of the
    model's judgement, which does not exist.

(f) EVALUATION WORK NOT YET DONE (item 14)
    - The corpus is 141 hand-labelled cases. `context_sources` shows
      `remembered_people` and `admin_activity` render 0 times — by design
      (DB-backed, excluded by name in `_CONTEXT_DB_BACKED`), but they have no
      end-to-end coverage at all.
      `provided_before` 0.425 / `provided_after` 1.0.
    - No latency budget is asserted for the READER LAYER as a whole (per-reader
      means are reported: resolver ~74-90 us/case, when ~46 us, entity ~40 us,
      polarity ~58 us, object ~120-220 us, all in-process and noisy).
    - The benchmark scores no model behaviour. Every "Nexus understands better"
      claim rests on the deterministic layer plus the invariant that the model
      receives it. There is no live-probe harness for the prompt's EFFECT on the
      model. The owner's standing preference (see the deploy-with-live-probe
      memory) is a live end-to-end probe over "tests pass" — that has not been
      built for this work.

4. OPEN QUESTIONS / THREADS
--------------------------------------------------------------------------------

4.1 THE role-two-admins TIE-BREAK THREAD  (RESOLVED in S — see §1.2c)
    Corpus case `role-two-admins` («ادمینه رو محدود کن» with two admins in the
    room) reads `ambiguous: true` BY DESIGN — the resolver refuses to pick
    between two people who genuinely hold the role. The question was whether the
    room's REPLY CONVERGENCE should be able to break that tie. RESOLVED: it must
    NOT. `_about_focus` fires only on a unanimous, repeated signal (>= 2 replies,
    all aimed at one person) and is scoped to ANAPHORIC expressions (far
    demonstrative or the object clitic); «ادمینه» is a ROLE expression, so
    `_about_focus` does not run for it — and that disjointness is the invariant,
    not an accident. A role signal must never run, replace or override the
    convergence, and two holders of a role are an ask, never a choice. The
    behaviour was already correct, so S changed NO production code; it pinned the
    reading with 4 corpus cases and two should-be-zero metrics
    (`role_two_admin_confident_cases`, `role_focus_used_cases`). See §1.2c.

4.2 UNRESOLVED CORPUS / MEASUREMENT QUESTIONS
    * §2.3 the requests.render reason wording (two routes, one sentence).
    * §2.2 objects.Object.source is unrendered — does the model need it?
    * Whether `remembered_people` / `admin_activity` need any end-to-end
      coverage (they are excluded from the render-coverage assertion by name).
    * The 141-case corpus is the whole labelled set; its growth is deliberate
      (a new case per newly-defensible reading). No case is currently known to
      be mislabelled.

4.3 ARCHITECTURE DECISIONS THAT STILL NEED EVIDENCE
    * (c) Whether the readers' output should be RECORDED with the pass, and if
      so in what shape and with what retention. This is a DB change, so it needs
      a forward/backward story and a rollback procedure — the first DB change
      since the foundation's `151b1e1`, and the first in the lettered
      increments. The `151b1e1` pattern is the precedent: additive columns via
      `_ensure_column`, never a `CREATE TABLE` change.
    * (d) The seam for content-aware scheduling that does not violate
      "`awareness.due` cannot see messages".
    * (e) Whether any model-routing change is measurable at all with the
      current evidence base.

6. END STATE — WHAT "COMPLETE" MEANS FOR THIS PROJECT
--------------------------------------------------------------------------------
Grounded in the actual architecture, not in ambition. The evolution is complete
when ALL of the following hold:

 1. THE DETERMINISTIC LAYER IS COMPLETE AND SCORED. Every reader (addressing,
    referents, discourse, temporal, room_state, entities, requests, objects)
    reports its reading as evidence, never a decision, pure at import time, and
    every sentence the prompt renders from them is scored against the reader's
    own finding — with a non-vacuity proof for each check. No block may order
    the model about a fact its reader does not hold.

 2. THE BENCHMARK IS THE ARBITER. tools/eval_intent.py over a labelled corpus
    is clean: top-1 accuracy, ambiguity recall and precision, wrong-but-
    confident == 0, act claimed precision and false positives == 0, object exact,
    edges exact, every should-be-zero metric at zero, and every floor asserted
    in tests/test_intent_eval.py. The corpus grows by one case per newly
    defensible reading; floors move on purpose by editing the corpus.

 3. THE PROMPT IS BOUNDED AND HONEST. The assembled context stays under the
    1500-character ceiling with per-source budgets; every source that can render
    does render in the benchmark (or is excluded by name and justified); the
    calendar renders first; nothing claims more than its reader found.

 4. THE PASS REMEMBERS WHAT IT READ (T). The readers' output survives the pass
    in a bounded, additive, rollback-safe form, so the server can answer "what
    did I read in that message?" without re-deriving it — and the model's
    structured understanding (intent, about) and the server's deterministic
    reading are joined rather than merely printed beside each other.

 5. SCHEDULING SPENDS THE RATIONED CURRENCY WELL (U). Within the SAME 200
    requests, the pass goes to the rooms that most warrant it, using evidence —
    without violating "awareness.due cannot see messages", without starving any
    room, and without adding a model call.

 6. EVERY BOUNDARY IN §1.3 AND AgentMD §53.7 STILL HOLDS. Readers are evidence;
    awareness_context is the only importer; Intent and Awareness are not
    authority; no message content in logs; OFF means off on every path; the
    window stays bounded; identity comes from the Telegram id and nothing else;
    Gemini workload isolation intact; cross-user/cross-group/cross-private
    isolation intact.

 7. IT IS VERIFIED ON THE RUNTIME, NOT ONLY IN TESTS. Every runtime-path
    increment (T, U, and anything after) has a self-cleaning live end-to-end
    probe with before/after numbers, per the owner's standing preference.

 8. main IS INTACT AND THE BRANCH IS INDEPENDENT. The rollback base
    00c5d1dd412e033c6ac15599b28bc0fbcb54d709 is untouched AND is an ancestor of
    the branch (verified with `git merge-base --is-ancestor`), so the whole
    evolution reverts by leaving the branch unmerged; every increment is also
    individually revertable; nothing is merged or deployed without the owner's
    explicit instruction.

Explicitly NOT part of "complete": dropping to a smaller model, adding keyword
detectors, replying to everything, trading a security property for coverage,
running concurrent passes, unbounded history, or any change to model routing
that is not proven by a measurement.
